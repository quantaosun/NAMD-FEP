From PDB 6I5I to ΔΔG

This deck documents the 6I5I relative binding free energy project in the NAMD-FEP repo. 15 slides. The real production run is executed by 6I5I_DUAL_FEP/run_all.sh on a single V100.

The system: CLK1 + inhibitor 12H (PDB 6I5I)

PDB 6I5I — crystal structure of human CLK1 in complex with a furo[3,2-b]pyridine compound 12H (ligand residue H3E).

  • Protein: CDC-like kinase 1 (dual-specificity Tyr/Ser-Thr protein kinase, EC 2.7.12.1)
  • Resolution 1.60 Å, engineered/phospho-regulatory kinase domain, chain A
  • CLK1 regulates alternative splicing by phosphorylating SR proteins — oncology target
  • Ligand 12H: furo[3,2-b]pyridine, ATP-competitive kinase inhibitor

Medicinal-chemistry question

We swap one substituent on the inhibitor and ask: does the analogue still bind, and by how much?

Concretely: replace the N-methyl of 12H by N–H (desmethyl analogue). Compute the change in binding free energy ΔΔGbind.

Reproduce the setup from repo 6I5I_DUAL_FEP/ — no FEPrepare / Maestro / LigParGen required.

CLK1 = CDC-like kinase 1. 6I5I deposited 2018, 1.6 Å. Ligand compound 12H is the co-crystallised furo-pyridine inhibitor; in our prep the ligand PDB residue was renamed UNL. Reference ligand keeps the methyl; mutant is the desmethyl N-H analogue.

The modification: one N–CH₃ becomes N–H

  • Reference: ring nitrogen N4 is N-methylated (–CH₃ = C12 + H7–H9).
  • Mutant (desmethyl): the methyl is removed → N4 carries a single H (H17).
  • Same scaffold, different end state → an ideal alchemical perturbation: the ligand never leaves the pocket.
In the dual-topology representation the scaffold is shared (present once) and only the N4 substituent differs. Bookkeeping from the FEP file: vanish set = {C12,H7,H8,H9} (B=-1), appear set = {H17} (B=+1).

Relative binding free energy — the thermodynamic cycle

  • ΔGbind of each ligand needs an absolute solvation + complex computation; their difference cancels most systematic error.
  • Only two alchemical legs are simulated: the mutation inside the complex and inside water.
  • Output: relative change in affinity between two chemically related ligands — the quantity medicinal chemists rank candidates by.
ΔΔG = ΔG_complex − ΔG_solvent. Both legs are computed by the same alchemical engine (identical force fields, same λ windows) so the difference is high-precision.

Free-energy perturbation (Zwanzig) — the idea

How to read it

  • We interpolate the Hamiltonian between end states with a coupling parameter λ: V(λ) turns the methyl off and the N–H on.
  • One simulation is run at λi; the energy ΔV = Vi+1 − Vi is evaluated on each frame → a Boltzmann-weighted exponential average.
  • The average is only reliable when the two neighbouring states overlap — hence many small windows.

Why FEP for RBFE

  • Alchemy bridges states that are hard to reach by brute-force sampling (no ligand association).
  • Works when the perturbation is local (one functional group) and well-equilibrated.
Zwanzig 1954. The ⟨·⟩_A average means configurations are sampled at state A but the energy difference to state B is re-weighted. Small perturbations → fast convergence; big ones need intermediates.

Windows & estimators: split the path, combine the pieces

  • 0 → 1 is cut into 15 windows; each runs a short MD and hands a distribution to the next.
  • BAR (Bennett Acceptance Ratio) combines forward and backward energies per window; both directions are run (λ 0→1 and 1→0) and their agreement is the hysteresis check.
  • Windows denser near λ=0 and λ=1, where electrostatics / soft-core VdW change fastest. ΔG = Σᵢ ΔGᵢ, each ΔGᵢ = −(1/β)ln⟨e^(−βΔVᵢ)⟩ᵢ.
Lambda set used: {0, .045, .09, .14546, .22425, .30303, .38182, .46061, .5394, .61819, .697, .77576, .85455, .91, .955, 1}. 250k steps (0.5 ns) per window; 50k steps flagged for equilibration (alchEquilSteps) and discarded by ParseFEP/BAR.

Dual topology: one core, two substituents

NAMD default: dual topology (singleTopology off)

  • The common core is present once (always fully interacting).
  • The atoms that differ — the methyl (ref) and the N–H (mut) — are both present and switched on/off through λ:
  • λmethyl (C12H₃)N–H (H17)common core
    0 (reference)interactingdummyinteracting
    1 (mutant)dummyinteractinginteracting
  • VdW of the disappearing atom is soft-cored (avoid end-point singularities); charges decouple gradually.

Trade-offs

  • Easiest to build (no shared-template choreography of the two ligands).
  • The "dummy" atoms interact with nothing — slight waste, but well supported in NAMD.
  • Alternative single topology mutates atoms in place; we use dual for robustness here.
In NAMD this is alchemical-type FEP with alchDecouple off for the RBFE perturbation (keeps the ligand core charged and coupled; only the methyl↔H swap is perturbed).

How λ-dependence is written: the .fep B-factor column

# ionized.fep — NAMD reads the tag via
#   alchFile ionized.fep · alchCol B
# (the PDB B-factor column re-purposed
#  as an alchemical mask)
HETATM ... UNL  C12 ... -1.00  # VANISH  methyl
HETATM ... UNL  N4  ...  0.00  # COMMON  scaffold
HETATM ... UNL  H17 ... +1.00  # APPEAR  N-H

Only the end-state substituents are tagged; protein, water, ions and the shared core are B = 0.

The encoding

  • B = −1 present in the reference, vanished at λ=1 (methyl)
  • B = 0 common / environment (protein · water · scaffold)
  • B = +1 appears only in the mutant (N–H)
  • Written from ionized.pdb by a deterministic Python pass — no hand edits.

Gotcha: both end-state atoms (methyl and N–H) must be present in the PSF at once — this is the essence of the dual topology.

The vanishing methyl atoms still exist in the topology but their nonbonded terms are scaled to zero by the alchemical λ. The appearance/annihilation is controlled purely by the B column here.

End-to-end preparation in three plain-Python scripts

protein.pdb
+ ref / mut ligand→ prepare_hybrid.py
chemical map + N-frame Kabsch→ hybrid.rtf/prm/pdb
(one dual-topology ligand)→ build_system.py
psfgen · solvate · ionize→ complex/ & solvent/
ionized.{psf,pdb}→ write_fep_inputs.py
.fep · fep.tcl · .namd→ run_all.sh

prepare_hybrid.py

  • Maps methyl / N–H by local chemical environment — graph isomorphism fails on the symmetric ring.
  • Places the new N–H using a local N-frame Kabsch fit.
  • Merges CHARMM-compatible ligand params (methyl + N–H + cross terms) into hybrid.rtf/prm.

build_system.py · write_fep_inputs.py

  • psfgen: protein is split at a disordered gap (412→416) into segments P1+P2, then ligand added.
  • Solvate (TIP3P) + auto-ionize → complex & pure-solvent boxes.
  • Mark B-factors → ionized.fep; write fep.tcl (16 λ) and 8 .namd configs.

Replaces the Feprepare web server, Maestro and LigParGen. numpy-only; no RDKit, no GUI.

Workflow in repo: python3 prepare_hybrid.py && python3 build_system.py && python3 write_fep_inputs.py, then bash run_all.sh. Water/ions use toppar/par_water_ions_clean.prm because NAMD cannot parse the .str topology+param stream.

Force-field stack

  • Protein: CHARMM36m (+ lipid / carb / na toppar as needed)
  • Ligand: CHARMM-compatible small-molecule parameters (ca/na/c3/hn/os …, CGenFF-style) in hybrid.rtf/prm
  • Water / ions: par_water_ions_clean.prm
  • PME electrostatics, 12 Å cutoff, switching at 10 Å, TIP3P + rigid bonds (2 fs)

Sampling — 300 K Langevin dynamics (NVT → NPT), well-equilibrated before the production windows begin.

The two legs are run with identical settings so their difference is meaningful. GPU-resident integration handles all nonbonded work; the ligand-only solvent box is latency-bound, not size-bound.

Compiling NAMD 3.0.3 for the V100 (GPU-resident)

./config Linux-x86_64-g++.gpuresident \
  --charm-arch multicore-linux-x86_64 \
  --with-single-node-cuda \
  --cuda-prefix /usr/local/cuda-11.8 \
  --cuda-gencode arch=compute_70,code=sm_70
make -j32
  • NAMD 3.0.3 + bundled Charm++ 8 (multicore arch), TCL/FFTW2 libs; host Ubuntu 20.04, CUDA 11.8, V100 sm_70.

The one flag that matters

Plain --with-cuda silently disables GPU-resident integration. Use --with-single-node-cuda — it defines NODEGROUP_FORCE_REGISTER and unlocks the GPUresident path (gated in src/SimParameters.C).

Without it: FATAL: GPUresident not supported on regular multicore builds.

Build gotcha: prebuilt FFTW2 archives are not -fPIC → link fails on Ubuntu 20.04 PIE. Rebuild FFTW 2.1.5 with -O3 -fPIC.

No Fortran is needed for NAMD 3.x (that resolves the gfortran note). Binary: Linux-x86_64-g++.gpuresident/namd3. Keep the plain -g++ build only for CPU comparison.

Performance: GPU-resident, and fewer threads is faster

Counter-intuitive but reproducible — in GPU-resident mode throughput is ~inversely proportional to the PE count. Run with +p1, not +p8.

  • Why: virtually all work is on the GPU; extra CPU PEs only add synchronization contention.
  • Old build +p8: 3.6 ns/day (plain) → GPU-resident +p1: 75.8 = ~21×
  • FEP leg ~22×; versus the very first baseline ≈ 45×.
  • Physics not sacrificed: single-point energy agrees with the CPU build to ~8 s.f.
Table measured on the 64,651-atom complex, identical configs: +p1 75.8, +p2 59.5, +p4 27.2, +p8 13.2, +p16 6.3, +p32 2.7 ns/day. stepspercycle etc made no difference — PE count is the whole story. GPU memory is not the limit (~590 MiB of 16 GiB used).

Runtime on one V100 — projected, sequential

Complex ≈ 47 ns/day · solvent ≈ 59 ns/day (0.0037 / 0.0029 s·step⁻¹), GPU-resident +p1.

Why the solvent leg is not ~13× faster

  • 5,013-atom solvent leg is latency-bound on the V100 — it saturates near ~59 ns/day regardless of size.
  • GPU memory is not a bottleneck (~590 MiB peak vs 16 GiB free); only a faster GPU (A100/H100) or fewer PEs helps.
  • Full job (both legs, both directions): ≈ 14–16 h wall-clock.

On the original ~1.7 ns/day baseline this would have taken ~25–30 days. The GPU-resident fix + +p1 rule is what makes daily FEP iteration feasible.

Production launch: complex nvt→npt→md_forward→md_backward, then solvent, run sequentially by run_all.sh. Logs stream to per-stage .log; .fepout/.coor/.dcd/.restart accumulate per leg.

Turning trajectories into a number: analysis & next steps

From .fepout to ΔΔG

  • Parse md_forward / md_backward.fepout (both legs).
  • BAR per window → ΔGcomplex, ΔGsolvent;
  • ΔΔG = ΔGcomplex − ΔGsolvent ± hysteresis / bootstrap.

Checks — forward vs backward agree (converged); ΔG smooth across λ; compare with experiment.

Extend — MBAR over the same windows; repeats for statistics; score a series of analogues with the same prep scripts.

Take-home. ① one local perturbation → two alchemical legs; ② dual-topology NAMD + a B-factor mask needs only scaffold + end-state atoms; ③ a GPU-resident build run with +p1 turned a ~30-day job into an overnight one — and more threads would have made it slower.

After the run completes, analysis follows the same recipe as T4L_RBFE output files: BAR between neighbouring windows using forward+backward, reporting ΔG per leg then ΔΔG.
